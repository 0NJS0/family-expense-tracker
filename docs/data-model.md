# Data model

Source of truth: `backend/app/models/` and the Alembic migrations in
`backend/alembic/versions/`. A test (`test_models_match_migrations`) fails if
the two diverge.

## Conventions

- UUID primary keys, generated by the server, except `transactions.client_id`,
  which the client generates.
- Every timestamp is `timestamptz`; `created_at` and `updated_at` are set by the
  database.
- Enumerations are `VARCHAR` + `CHECK` constraints (cheaper to evolve than
  PostgreSQL enums).
- Constraint names follow a fixed naming convention, so migrations are
  deterministic.
- Every foreign key is `ON DELETE RESTRICT`, except `refresh_tokens → auth_sessions`.
  Financial history is never deleted by cascade.

## Tables (Milestone 1)

| Table | Purpose | Key constraints |
|-------|---------|-----------------|
| `users` | Login identities | unique lowercase `username`; Argon2id `password_hash`; `preferred_language ∈ {bn,en}` |
| `households` | A family's books | `currency = 'BDT'`; `timezone` (IANA); `week_start 0–6` |
| `memberships` | User ↔ household with role | unique `(household_id, user_id)`; `role ∈ {admin, member, viewer}`; `deactivated_at` (removal from the household without deleting history, migration 0002) |
| `invitations` | Single-use join links | unique SHA-256 `token_hash`; `expires_at`; `accepted_at` |
| `auth_sessions` | One login on one device | `expires_at` (absolute); `revoked_at`, `revoke_reason` |
| `refresh_tokens` | Rotating refresh tokens | unique SHA-256 `token_hash`; `used_at` marks rotation |
| `accounts` | Labels for where money is (cash, bank, mobile wallet, other); **no account numbers or bank details are stored**. New households get নগদ, বিকাশ (provider bKash) and ব্যাংক automatically | unique `(household_id, lower(name))`; owner must be a member (composite FK); `NULL` owner = shared; `is_private` (only the owner and admins see it; `CHECK` it has an owner, migration 0004) |
| `opening_balances` | Starting balance per account | PK `account_id` (at most one); bounded signed `BIGINT`; composite FK to the account in the same household |
| `categories` | Bilingual income/expense categories | `kind ∈ {income, expense}`; unique `(household_id, kind, lower(name_en))`; unique `(household_id, id, kind)` as an FK target |
| `transactions` | Income, expense, transfer | see below |
| `audit_events` | Append-only audit trail | trigger rejects `UPDATE` and `DELETE` |
| `budgets` | Monthly budget timeline per scope (whole household when `category_id` is `NULL`, else one expense category): "from `effective_month` on, the budget is `amount_poisha`" (`NULL` = removed) | unique `(household_id, COALESCE(category_id, nil), effective_month)`; first of month; bounded amount; `warn_percent` 1–99 (migration 0005) |
| `budget_alerts` | A threshold of a budget crossed in a month | unique `(household_id, scope, month, threshold_percent)`: each alert at most once (migration 0005) |
| `recurring_rules` | Rent, salary, bills: what, how much, how often | same shape `CHECK` and composite FKs as transactions; `frequency`, `interval` 1–12, `start_date`, `end_date`, `auto_post` (default false), `paused_at`, `next_index`/`next_due_date`, `version` (migration 0006) |
| `recurring_occurrences` | One due date of a rule: `pending`, `posted` (with its transaction) or `skipped` | unique `(rule_id, due_date)` makes generation idempotent; `posted` ⇔ `transaction_id` set (migration 0006) |

### `transactions`

| Column | Notes |
|--------|-------|
| `id` | server UUID |
| `household_id` | owning household |
| `client_id` | client-generated idempotency UUID; unique per household |
| `request_fingerprint` | SHA-256 of the canonical creation payload, to detect a `client_id` reused for different data |
| `created_by_user_id` | who entered it |
| `attributed_user_id` | whose money it is; composite FK to `memberships` in the same household |
| `type` | `income`, `expense` or `transfer` |
| `amount_poisha` | `BIGINT`, `> 0` and `≤ 100,000,000,000` |
| `category_id` | required for income and expense, `NULL` for transfers |
| `account_id` | the account (the source for transfers) |
| `destination_account_id` | transfers only; must differ from `account_id` |
| `occurred_at` | when it happened (the client's claim) |
| `note` | optional private text, max 500 characters |
| `version` | starts at 1, incremented on every edit or void; optimistic concurrency |
| `created_at`, `updated_at` | server time; distinct from `occurred_at` |
| `voided_at`, `voided_by_user_id`, `void_reason` | all `NULL` or all set (`CHECK`) |

Database-level guarantees, independent of application code:

- `ck_transactions_shape`: a transfer has a different destination and no category;
  income and expense have a category and no destination.
- Composite foreign keys `(household_id, account_id)`,
  `(household_id, destination_account_id)` and
  `(household_id, attributed_user_id)` make cross-household references
  impossible.
- `(household_id, category_id, type) → categories(household_id, id, kind)` makes
  an expense category unusable for income and vice versa. For transfers,
  `category_id` is `NULL`, so the key is not checked (`MATCH SIMPLE`).

Indexes: `(household_id, occurred_at)` for listing and reports, plus single
columns on `account_id`, `destination_account_id`, `category_id` and
`attributed_user_id`.

## Migrations

| Revision | Change | Data impact |
|----------|--------|-------------|
| 0001 | initial schema and append-only audit trigger | none |
| 0002 | `memberships.deactivated_at` (nullable) | additive only |
| 0003 | index `(household_id, updated_at, id)` on transactions for the change feed | additive only |
| 0004 | `accounts.is_private` (default false) + `CHECK` owner | additive; every existing account stays visible |
| 0005 | `budgets`, `budget_alerts` | new tables |
| 0006 | `recurring_rules`, `recurring_occurrences` | new tables |
| 0007 | `notification_preferences` | new table |
| 0008 | `receipts`; unique `(household_id, id)` on transactions (always true: `id` is the key) | new table, additive key |
| 0009 | `ai_reports` | new table |

## Milestone 5 tables

| Table | Purpose | Key constraints |
|-------|---------|-----------------|
| `notification_preferences` | One row per person and household: daily reminder (default off), missing-entry reminder (default on), time (default 20:00), due bills, budget alerts | PK `(household_id, user_id)`; composite FK to `memberships` |
| `receipts` | A file attached to a transaction: type, size, SHA-256 of the upload and of the stored file, private storage key; OCR status, private text, suggested amount and date; soft removal | composite FK `(household_id, transaction_id)`; `content_type` JPEG or PDF only; unique `(transaction_id, upload_sha256)` among non-removed (retries); unique `storage_key` |
| `ai_reports` | A monthly AI summary: facts (JSONB, computed in code), text, status `queued/running/done/rejected/failed`, problem, model, attempts, retry time | unique `(household_id, period_start, language)`; first of month; `language ∈ {bn, en}` |
